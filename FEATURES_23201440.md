## F-04 — WebGL Epistemic Graphs (Sprint 1)

**Acceptance criterion:** *"The graph interface renders a large number of nodes
using WebGL without major UI freezing."*

**Implementation**
- Renderer: Sigma.js (WebGL) — [apps/frontend/src/graph/sigma-config.ts](apps/frontend/src/graph/sigma-config.ts),
  [apps/frontend/src/hooks/useLineageGraph.ts](apps/frontend/src/hooks/useLineageGraph.ts),
  [apps/frontend/src/components/LineageGraph.tsx](apps/frontend/src/components/LineageGraph.tsx)
- Layout: ForceAtlas2 with Barnes-Hut approximation above ~300 nodes, so the
  O(n²) repulsion doesn't stall the platform-wide graph.
- Loaded client-side only ([GraphCanvas.tsx](apps/frontend/src/components/GraphCanvas.tsx))
  because Sigma touches `WebGL2RenderingContext` at module scope, which would
  otherwise crash static prerendering.

**Verified:** the platform graph renders **900 nodes / ~9,800 edges** on the
GPU with no console errors; hover-to-isolate, search, zoom and reset all
interactive.

## F-07 — Community-Detection Grouping (Sprint 2)

**Acceptance criterion:** *"Related nodes are grouped into logical clusters
using backend community-detection output."*

**Implementation**
- Louvain worker: [apps/python-worker/src/louvain.py](apps/python-worker/src/louvain.py),
  [apps/python-worker/src/graph_store.py](apps/python-worker/src/graph_store.py)
- Clusters over **lineage (`SEQUENCE_OF`) + co-tag (`HAS_TAG`)** edges,
  weighted 3:1, with every article node included (isolated nodes too) and a
  pinned `random_state` so cluster ids stay stable across polls.
- Result written back as `Article.clusterId` and surfaced by the graph API,
  which names each community after its dominant claim category.

**Live check**
```
worker heartbeat: nodes=900 lineage_edges=676 topic_edges=9360 communities=44
Neo4j: 900 articles, 900 with clusterId, 44 distinct communities
```
Every node is assigned; 44 coherent communities (e.g. "Security Analyst",
"Housing Analyst", "Climate Analyst") — verified purity sits at 35–100% per
community, i.e. Louvain is genuinely grouping cross-category story chains, not
merely echoing the tags back.

## F-11 — Cross-Tag Validation Matrix (Sprint 3)

**Acceptance criterion:** *"A claim cannot be resolved unless auditors from
non-overlapping expertise categories participate in the consensus."*

**Implementation**
- `EvaluateCrossTagConsensus`, `hasNonOverlappingPair`, `disjoint` in
  [apps/go-backend/internal/models/vote.go](apps/go-backend/internal/models/vote.go)
- Compares **whole tag sets** for disjointness (not just the first tag), and
  requires a genuinely non-overlapping pair on the winning side.
- Unit tests: [apps/go-backend/internal/models/vote_test.go](apps/go-backend/internal/models/vote_test.go)
  (same-tag ≠ cross-tag, overlapping multi-tag ≠ cross-tag, determinism).

**Live check** — one claim, three votes:
```
vote 1  Economic Analyst              -> 202 pending
vote 2  Economic+Labour (OVERLAPS)    -> 202 STILL pending   ← the key rule
vote 3  Security Analyst (DISJOINT)   -> 200 RESOLVED (verified)
```
The overlapping second vote correctly failed to resolve the claim; only the
disjoint third vote did. This is the exact behaviour the criterion requires.

## F-15 — Under Dispute Visual State (Sprint 3)

**Acceptance criterion:** *"An appealed article node changes to a pulsing
amber/orange visual state while the appeal is active."*

**Implementation**
- Backend: the graph API merges `hasActiveAppeal` from Postgres onto each node
  ([apps/go-backend/internal/models/graph.go](apps/go-backend/internal/models/graph.go),
  [apps/go-backend/internal/controllers/graph.go](apps/go-backend/internal/controllers/graph.go)).
- Frontend: an absolutely-positioned pulsing amber ring (`.dispute-pulse`)
  over each flagged node — [apps/frontend/src/components/LineageGraph.tsx](apps/frontend/src/components/LineageGraph.tsx),
  keyframes in [apps/frontend/src/app/globals.css](apps/frontend/src/app/globals.css).
  Ring positions use `framedGraphToViewport` and are clipped to the canvas so
  they track their node on pan/zoom.

**Live check:** 12 active appeals in the DB → the graph API flags **exactly 12
nodes** with `hasActiveAppeal: true`; the amber pulse renders over each
(confirmed in a browser screenshot).

## F-19 — Instant Global Leaderboards (Sprint 4)

**Acceptance criterion:** *"The leaderboard displays ranked journalists quickly
using Redis-backed sorted ranking data."*

**Implementation**
- Read path: `GET /leaderboard` reads a Redis **sorted set** via `ZREVRANGE`
  ([apps/go-backend/internal/controllers/leaderboard.go](apps/go-backend/internal/controllers/leaderboard.go),
  [apps/go-backend/internal/models/leaderboard.go](apps/go-backend/internal/models/leaderboard.go)),
  touching Postgres only to attach display names (NFR-3).
- Key `leaderboard:journalist_rank`
  ([apps/go-backend/internal/redisstore/client.go](apps/go-backend/internal/redisstore/client.go)),
  warmed from Postgres at boot so a restarted Redis or a SQL-seeded database
  never serves an empty board.
- UI: [apps/frontend/src/app/leaderboard/page.tsx](apps/frontend/src/app/leaderboard/page.tsx).

**Live check**
```

  Sofia Marchetti 181.5 · Lucia Ferreira 159.6 · Kenji Watanabe 148.3 …
```
